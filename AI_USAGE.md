# AI Usage

## Which tools

Claude Code (Claude Sonnet 5), used directly in an agentic session with real tool access — reading/writing files, running commands inside the project's own Docker containers, and driving a real headless browser against the running frontend.

## What it was used for

Effectively the whole build: planning the architecture and getting it reviewed against the brief before writing code, scaffolding and writing the Laravel backend (migrations, models, policies, services, controllers, Form Requests, API Resources, the centralized exception handling, the Pest test suite), the React/Redux frontend (RTK Query API layer, pages, components, the Vitest/MSW tests), the Docker Compose environment and its bootstrap entrypoint, the `.gitlab-ci.yml` pipeline, and this documentation set. Every piece of code in this repository was generated by, and reviewed by, this session — not hand-written and then explained after the fact.

## What was manually reviewed

This is a Claude Code session working directly in the repository, not a one-shot generation reviewed afterward — every file was written by running real commands against a real, running stack (Docker containers actually built and started, migrations actually run against real MySQL, the Pest suite actually executed, curl and a headless browser actually driven against the live API and frontend), and each step's real output shaped the next one. Concretely, verification wasn't "look at the code and reason about whether it's right" but:

- The full backend test suite was run repeatedly (51 Pest tests against real MySQL + Redis, no mocking) until genuinely green, not until the run merely completed.
- The idempotency and optimistic-locking behavior was checked twice — once through the automated Pest suite, and separately by hand with raw `curl` against the live Dockerized API (login, list/filter/search, create/update/assign a contact, trigger and inspect a real 409 version conflict, create an interaction and replay it with the same key, reuse a key with a different payload and confirm the 422) — specifically because these are the two properties the brief calls out as needing to actually work, not just look right on paper.
- Redis's fail-open behavior was checked for real, not just asserted in a mocked unit test: `docker compose stop redis`, then a real login and a real interaction-creation-plus-retry were driven against the live stack with Redis genuinely down, confirming both degrade correctly instead of 500ing.
- The frontend was driven in an actual headless browser against the live backend for both roles (login, contacts list with filters/sort/pagination, contact detail, adding an interaction, and confirming an agent's UI correctly hides team-lead-only controls) — not just typechecked and unit-tested in isolation.
- Pint and Larastan (backend) and oxlint/tsc (frontend) were run and their output fixed until clean, not left with suppressed or ignored warnings.
- The `.gitlab-ci.yml` pipeline was validated with `gitlab-ci-local` — every job actually executed in Docker (not just YAML-schema-checked) before being called done, which is what caught the four real pipeline bugs in entry 7 below; see README "Known limitations" for what that validation doesn't cover (a real GitLab runner).

## Rejected, corrected, or substantially changed AI-generated output

These are real corrections made during this session, each caught by actually running something rather than by inspection alone:

1. **A global idempotency-key uniqueness constraint would have let one user replay another user's interaction.** The first pass at the idempotency design used a single globally-unique `idempotency_key` column. Working through the design before implementing it surfaced the actual problem: two different users coincidentally (or maliciously) using the same key value would collide, and the "replay" behavior would hand user B a copy of user A's interaction. Changed the constraint to `UNIQUE(created_by, idempotency_key)` and added a test (`tests/Feature/Interactions/InteractionTest.php`, "two different agents may coincidentally use the same idempotency key without colliding") specifically for this.

2. **`fetchBaseQuery` doesn't send cookies or CSRF headers by default.** The first frontend auth pass assumed Sanctum's SPA cookie flow would "just work" once `credentials: 'include'` was set. Running the actual login flow against the real backend surfaced a 419 CSRF mismatch — RTK Query's `fetchBaseQuery` doesn't read `document.cookie` and forward it as a header automatically. Fixed by adding `getXsrfTokenHeader()`/`ensureCsrfCookie()` (`frontend/src/lib/csrf.ts`) and wiring `ensureCsrfCookie()` into every mutating request in the base query.

3. **A generated `search_blob` column added complexity without adding value.** An earlier design generated a computed column concatenating the searchable fields and put the FULLTEXT index on that instead of the columns directly. Once written, it was clear this added a maintenance surface (the generated-column expression has to be kept in sync with which fields are "searchable") for no actual benefit over a direct multi-column `FULLTEXT(name, email, phone, company)` index, which MySQL supports natively. Removed the generated column.

4. **`Contact::load('assignedAgent', [...])` — wrong method signature, caught immediately by actually calling the endpoint.** A first draft of `ContactController::show()` passed a relation name and an array of closures as two separate positional arguments to Eloquent's `load()`. This is invalid — `load()` takes one array. It compiled fine (PHP doesn't type-check this) and only failed at runtime with a `TypeError` two levels deep in Eloquent's relation-loading internals. Caught within minutes by actually hitting the endpoint with curl as part of the verification pass described above, not by static analysis — a good example of why the manual, real-request verification mattered here beyond what the type checker and test suite alone would have caught at that point (a test for this endpoint was added afterward).

5. **An `actingAs()`-based test that silently relied on framework internals that don't work the way assumed.** A test that called `$this->actingAs($userA)` and later `$this->actingAs($userB)` within the *same* Pest test, expecting the second call to fully switch the effective authenticated user for a subsequent request, failed unpredictably. Root-caused (via a minimal reproduction test, not guessing) to Sanctum's stateful-session guard not re-resolving the user from the second `actingAs()` call within one test in the way a naive reading of Laravel's testing docs suggests. Rather than fighting the framework, the test was restructured to seed the "first" state directly and only call `actingAs()` once — which is also, independently, better test design (one acting user per test, less coupled to auth-mechanism internals).

6. **Vitest 3.x and Vite 8 have an incompatible nested peer dependency, and `npm`'s own dependency resolver hit a real bug on top of it.** `vitest: ^3.0.0` resolved to a version whose bundled `vite` peer didn't match the project's own `vite@^8.3.0`, causing a TypeScript plugin-type mismatch in `vite.config.ts`. Fixing the version constraint to `vitest@^5.0.1` (which lists `vite@^8.0.0` as a supported peer) then hit a second, unrelated problem: npm 10.8.2's dependency resolver (`Arborist`) crashed with an internal `Cannot read properties of null (reading 'edgesOut')` error on this specific dependency graph — a known class of npm bug, not a project misconfiguration. Resolved by upgrading npm itself (to 11.x, then confirming with npm's own engine warning that Vitest 5 actually wants Node ≥22, which led to bumping `docker/frontend/Dockerfile` from `node:20-alpine` to `node:22-alpine`) rather than working around it by pinning an older, incompatible toolchain.

7. **The first version of `.gitlab-ci.yml` looked correct and would not have worked — caught only by actually executing it.** Writing GitLab CI YAML that's merely schema-valid is easy and was not treated as sufficient; the pipeline was run for real with `gitlab-ci-local` against real Docker containers, which surfaced four real, independent bugs that pure inspection would have missed:
   - `pecl install redis` prompts interactively (igbinary/msgpack/etc. support) even under a non-interactive shell, hanging the job. First fix: pipe `yes ''` into it.
   - That fix's output was chained as `pecl install redis >/dev/null 2>&1 && docker-php-ext-enable redis` — silencing it hid that the extension wasn't actually loading, and the job only failed five minutes later with 51 tests erroring "Class Redis not found," instead of failing loudly at the install step where the actual problem was. Fixed by splitting the chain onto separate, unsilenced lines and adding an explicit `extension_loaded('redis')` check.
   - That check was first written as `php -m | grep -q redis` — under a `pipefail` shell, `grep -q`'s early exit can SIGPIPE the still-writing `php -m`, and the pipeline reports that as a failure even though the check itself passed. Fixed by checking with a plain `php -r` one-liner instead of a pipe.
   - The exact same SIGPIPE class of bug was then hit again in `yes '' | pecl install redis` itself once the check above made it visible — `yes` gets killed by SIGPIPE the moment `pecl` stops reading, and that's reported as *that line's* failure regardless of whether `pecl` itself succeeded. Fixed by not treating that specific line's exit code as authoritative, since the dedicated `extension_loaded()` check two lines later is the real, reliable gate.

   Each of these was found by an actual job failing with an actual error message, fixed, and re-run until genuinely green — not reasoned about in the abstract. The final state: all three backend jobs (`backend:install`, `backend:lint`, `backend:test` — 51/51 tests, against real `mysql`/`redis` services) and the full `frontend:*` chain pass under `gitlab-ci-local`.

8. **The "unassigned contacts" filter silently 422'd on every use — a JS-boolean-to-query-string bug caught only by actually clicking the checkbox in a browser.** `ListContactsPage` builds `{ unassigned: unassigned || undefined }` where `unassigned` is a JS boolean; RTK Query's `fetchBaseQuery` serializes that into the query string as the literal word `"true"`. Laravel's `boolean` validation rule doesn't accept that string (only `1`/`0`/`"1"`/`"0"`/`true`/`false`), so the backend rejected the request with a 422 — which the frontend then rendered as an empty result list, indistinguishable at a glance from "correctly found zero unassigned contacts." This passed code review, passed the type checker, and would have passed a superficial manual check ("click the checkbox, see an empty-looking list, assume it's just because none are unassigned"). It was only caught by comparing the *actual network request* against what the backend expected, while systematically driving every filter on the page through a real browser against the live stack. Fixed in `contactsApi.ts` by converting the boolean to `'1'` at the query-building boundary, where every caller benefits from the fix regardless of what state shape they pass in.

9. **`ReassignControl`'s "Assigned agent" label wasn't programmatically associated with its `<select>` — caught by browser automation trying to find the control by its accessible name.** Every other form control in this codebase wraps its `<label>` around the input (or uses `htmlFor`/`id`), which is what gives it an accessible name a screen reader (or a testing tool driving by role/label, the same mechanism) can find. `ReassignControl.tsx` instead had the label and `<select>` as plain unconnected siblings — visually fine, but with no programmatic link between them, so assistive tech would announce the select with no name at all. Found while re-running the full manual QA script end-to-end for this session's "test everything" pass: a `getByLabel('Assigned agent')` lookup that should have worked (and did on every other labeled control in the app) timed out. Fixed by wrapping the label around the select, matching the pattern already used in `LoginPage.tsx` and `ContactFormPage.tsx`; re-verified the reassignment flow end-to-end afterward and re-ran Vitest/tsc/oxlint to confirm nothing regressed.

10. **A login attempt with the backend completely unreachable failed silently — no error banner, no feedback at all — caught only by actually stopping the `app` container and watching.** `ensureCsrfCookie()` (`lib/csrf.ts`) calls `fetch()` directly, with no `try`/`catch`; `baseApi.ts`'s `baseQueryWithAuthHandling` `await`s it before every mutating request but didn't catch a rejection either. When the backend is fully down (not an HTTP error status, but a network-level failure — nginx's own 502 page has no CORS headers, so the browser reports it as a blocked CORS request), that `fetch()` throws. The throw propagated out of the custom `baseQuery` function entirely, bypassing the normal `FetchBaseQueryError` shape that `toApiError()` knows how to read — so the mutation's error state existed but matched none of `toApiError()`'s branches, and `LoginPage`'s `{apiError && <ErrorBanner .../>}` rendered nothing. Observable symptom: the "Sign in" button disables, re-enables, and then — nothing. No banner, no redirect, no console exception (the rejection was technically caught by RTK Query's own internals, just reshaped into something the UI didn't recognize). Found by stopping the `app` container mid-session and sampling the login form's state every 1.5s with a script rather than a single fixed wait, which is what made the "button recovers but nothing else happens" window visible instead of just looking like a slow request. Fixed by wrapping the `ensureCsrfCookie()` call in a `try`/`catch` inside `baseQueryWithAuthHandling` and, on failure, returning `{ error: { status: 'FETCH_ERROR', error: String(err) } }` — the exact shape `fetchBaseQuery` itself already produces for a network failure, which `toApiError()` already handles. Re-verified against the same live, stopped-container scenario: the banner now reads "Could not reach the server. Check your connection and try again." within ~3s, and a normal login succeeds once the container is back.
